2、整体分析

  1. config.json

    1. 存储模型架构元数据，包括网络层数，隐藏维度，注意力头数，词表大小，激活函数类型等参数

  2. 模型权重文件：torch 和 hf 权重文件

    1. pytroch_model.pth: 用于保存模型权重参数的二进制文件，以字典的形式保存，键为层名称，值为对应的权重张量数据。

    2. model.safetensor：和pth权重文件的功能相同，区别是采用了安全序列化格式，避免反序列化漏洞风险。

    3. 分片权重文件：对于超大型的模型权重，会被分割成多个文件，解决单个文件体积限制问题。

  3. 分词器相关

    1. tokenizer_config.json: 分词器类型、特殊标记的定义

    2. tokenizer.json: 将分词器的所有配置信息，包括词汇表，合并规则，归一化，预分词，后处理等打包在一起，目的是让训练和推理过程中的分词行为完全一致。

  4. 文本生成参数配置文件 

    1. generation_config.json：定义文本生成策略，包括温度，top-p等超参数。

tokenizer.json

文件定义了分词器的所有配置

  1. added_tokens: 原有词汇表基础上额外添加的特殊token([PAD] [CLS])

  2. post_processor: 后处理模板，设置单句，双句对输入时输入时自动添加[cls] 和 [sep]

  3. decoder：解码器类型

  4. model：底层分词器模型 的类型及其参数。

    1. Vocab: 定义了词汇表，其中key为token的字符串，value为对应的id。

    2. merges：定义了子token合并成更长token的规则。

special_tokens_map.json

文件定义了与文本序列处理相关的特殊token

  1. bos_token (Beginning of Sentence Token): 序列开始标记，文本序列的起始位置

  2. eos_token (End of Sentence Token)： 序列结束标记，表示文本序列的结束位置。

  3. eop_token (End of Paragraph Token): 段落结束标记，表示段落结束的特殊标记

  4. pad_token (Padding Token): 填充标记，它将用于文本序列填充到相同长度时使用的特殊token。tokenizer.json 文件解析。 

3、具体分析

3.1 config.json

作用：用于描述模型的结构、超参数、训练方式、特殊行为等信息，在加载模型时自动解析并构建模型实例。

{
  // 使用的模型架构名称
  "architectures": [
    "Qwen2ForCausalLM"
  ],
  // 注意力层的dropout比例
  "attention_dropout": 0.0,
  // 句子起始（BOS）token的ID
  "bos_token_id": 151643,
  // 句子结束（EOS）token的ID
  "eos_token_id": 151645,
  // 隐藏层激活函数
  "hidden_act": "silu",
  // 隐藏层维度
  "hidden_size": 5120,
  // 参数初始化范围
  "initializer_range": 0.02,
  // 前馈网络中间层的维度
  "intermediate_size": 27392,
  // 最大位置编码长度
  "max_position_embeddings": 32768,
  // 支持滑动窗口的最大层数
  "max_window_layers": 35,
  // 模型类型标识
  "model_type": "qwen2",
  // 注意力头的数量
  "num_attention_heads": 40,
  // Transformer层的数量
  "num_hidden_layers": 64,
  // key-value注意力头的数量（用于分组注意力等）
  "num_key_value_heads": 8,
  // 量化相关配置
  "quantization_config": {
    // 量化位数
    "bits": 4,
    // 量化分组大小
    "group_size": 32,

🧠 一、基本模型规格

参数 含义 说明
model_type: "qwen2" 模型类型 来自阿里达摩院的 Qwen2 系列
architectures: "Qwen2ForCausalLM" 架构 自回归语言模型（Causal Language Model）
hidden_size: 5120 每层维度 大型模型（估算 20B 参数级别）
num_hidden_layers: 64 Transformer 层数 层数非常深
num_attention_heads: 40 注意力头数
num_key_value_heads: 8 KV 分组数量 表明采用了 Grouped Query Attention (GQA)
intermediate_size: 27392 FFN 层维度
vocab_size: 152064 词表大小 包含中文/英文等多语言词表

🧠 二、上下文和位置处理

参数 含义
max_position_embeddings: 32768 最大位置嵌入（理论最大上下文长度）
sliding_window: 32768 实际窗口大小
max_window_layers: 35 可支持滑动窗口的层数
rope_theta: 1e6 用于 RoPE（旋转位置编码）的频率参数（适配长上下文）

📌 说明：这是一个支持超长上下文（32K token）的模型，适合：

  • 读大文档（PDF/合同/代码）

  • 长对话历史保持上下文连贯

  • 文本审校、知识提取

⚙️ 三、优化与量化配置

参数 含义
quantization_config.bits: 4 4-bit 量化
quant_method: awq 使用 AWQ（Activation-aware Weight Quantization）
group_size: 32 每组参数量化块大小
version: gemm 量化内核类型，基于 GEMM
zero_point: true 使用 Zero-point 对称量化
torch_dtype: "float16" 半精度 float16 运算

📌 说明：这说明这个模型是经过 4bit AWQ 量化优化的版本，意味着你可以：

  • 在消费级显卡（比如 24G 显存）运行

  • 延迟更低，推理速度快

  • 部署成本降低

3.2 generation_config.json

推理参数（生成策略）配置文件,  用于控制模型生成文本时的行为（例如采样策略、终止符号、重复惩罚等）， 这段 JSON 是模型的“生成策略说明书”，控制模型如何从输入中“说出”下一句话。

{
  // 起始标记的token id
  "bos_token_id": 151643,
  // 是否使用采样生成
  "do_sample": true,
  // 结束标记的token id列表
  "eos_token_id": [
    151645,
    151643
  ],
  // 填充token的id
  "pad_token_id": 151643,
  // 重复惩罚系数
  "repetition_penalty": 1.05,
  // 采样温度
  "temperature": 0.7,
  // top-k采样参数
  "top_k": 20,
  // top-p采样参数
  "top_p": 0.8,
  // transformers库的版本
  "transformers_version": "4.38.2"
}

🔍 字段解析与作用

参数名 示例值 含义与作用
bos_token_id 151643 Begin Of Sequence，生成起始标记 token ID
eos_token_id [151645, 151643] End Of Sequence，遇到这些 token ID 时停止生成
pad_token_id 151643 用于 padding（对齐序列）时使用的 token ID
do_sample true 启用采样（否则是贪婪/beam search）
temperature 0.7 控制采样随机性（值越低越确定）
top_k 20 限制每一步采样时最多考虑前 20 个概率最高的 token
top_p 0.8 nucleus sampling（只考虑累积概率 ≥ 0.8 的 token）
repetition_penalty 1.05 惩罚重复词语（>1 会降低重复出现 token 的概率）
transformers_version "4.38.2" 指明此配置兼容的 HuggingFace Transformers 版本

🧠 实际生成中它怎么用？

你加载模型后，如果该文件存在，Transformers 会自动读取这些参数并应用到 generate() 调用中：

from transformers import AutoTokenizer, AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2-7B")
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2-7B")

input_ids = tokenizer("你好，请帮我总结一下这段话：", return_tensors="pt").input_ids
outputs = model.generate(input_ids)
print(tokenizer.decode(outputs[0], skip_special_tokens=True))

如果目录下存在 generation_config.json，model.generate() 会默认读取其中的设置（如 top_k, temperature 等）。

你也可以手动覆盖它：

outputs = model.generate(
    input_ids,
    temperature=0.7,
    top_k=20,
    top_p=0.8,
    repetition_penalty=1.05,
    do_sample=True,
    max_new_tokens=256
)

✅ 你可以用它做什么？

  • 自定义生成风格：更随机或更确定、控制重复

  • 优化对话流畅性：结合 eos_token_id，能更自然地中止输出

  • 自动化部署：多个模型可统一读取生成策略文件

3.3 merges.txt

merges.txt 是 Hugging Face 模型中的一个 分词器（Tokenizer）文件，它是 Byte Pair Encoding（BPE） 分词算法的核心组成部分之一，配合 vocab.json 使用，决定了如何将文本分割成 token。

merges.txt 是 Hugging Face 模型中的一个 分词器（Tokenizer）文件，它是 Byte Pair Encoding（BPE） 分词算法的核心组成部分之一，配合 vocab.json 使用，决定了如何将文本分割成 token。

🧠 BPE 分词算法背景简述

Byte Pair Encoding (BPE) 是一种基于频率的子词（subword）分词方法，常用于：

  • GPT 系列（包括 OpenAI 模型）

  • RoBERTa、DistilBERT、Qwen、LLaMA、BLOOM 等 HuggingFace 模型

  • 适用于多语言、中文、代码等

📂 **merges.txt** 文件作用

定义每一步合并哪些子词，形成新的词片段（token），即：

  • 从原始字符逐步构建更大的常见子词

  • 保留高频组合、减少词表大小、提升表示能力

🧾 文件内容格式示例

#version: 0.2
t h
th e
he r
re s
es t
...

每一行是一个 合并规则（merge rule），格式为两个空格分隔的子词（symbol）：

A B

表示 A B → AB 的合并操作。模型在分词时会按这些规则顺序地将字符对合并成 token，直到无法合并为止。

🔄 与 vocab.json 的关系

文件 作用
vocab.json 保存最终的 token → id 映射（所有可用 token）
merges.txt 保存 BPE 合并规则（从字符构造这些 token 的路径）

二者共同定义了分词器的行为，缺一不可。

📦 应用举例：GPT 分词过程

假设原始文本是 "there"

  1. 初始字符序列：["t", "h", "e", "r", "e"]

  2. 第一次匹配合并规则：t h → th

  3. 变为：["th", "e", "r", "e"]

  4. 然后：th e → the

  5. 然后：the r → ther

  6. 然后：ther e → there → ✅ 完整 token

最终就是一个 token：there，对应 vocab.json 中的某个 ID。

🔍 怎么查看？

使用 HuggingFace Tokenizer API 查看分词器：

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2-7B")
print(tokenizer.tokenize("there"))

🛠️ 常见用途

作用 示例
✅ 自定义分词器 用你自己的 merges.txt + vocab.json 创建分词器
🧪 分析模型分词习惯 看哪些词被拆了，比如中文 数据处理 → 数, 据, 处理
📦 微调 tokenizer 用 HuggingFace tokenizers 工具重新训练 tokenizer

🧰 实战示例：创建自定义 BPE 分词器

from tokenizers import Tokenizer, models, trainers, pre_tokenizers

tokenizer = Tokenizer(models.BPE())
tokenizer.pre_tokenizer = pre_tokenizers.Whitespace()

trainer = trainers.BpeTrainer(vocab_size=10000, special_tokens=["<pad>", "<unk>"])
tokenizer.train(["your_corpus.txt"], trainer)

tokenizer.save("tokenizer.json")  # 里面包含 vocab 和 merges

✅ 总结一句话

merges.txt 是 HuggingFace BPE 分词器的“合并规则表”，告诉模型如何从字符组合成 token，它是 vocab.json 的构造过程记录，二者配合用于模型输入的分词处理。

3.4 model-00001-of-000XX.safetensors

model-00001-of-000XX.safetensors 是 Hugging Face 或类似框架在保存大型模型权重时生成的文件之一。其中XX值代表有多少个类似的权重文件，这个文件的 作用是保存模型的实际权重（参数）数据，是推理或训练时真正加载到模型中的核心内容。

📦 一句话概括

model-00001-of-000XX.safetensors 是保存 Transformer 模型参数的分片化 safetensors 文件，它是 .bin 的安全高效替代，用于多文件分布式加载大型模型。

🔍 文件组成与命名结构

比如你看到这样的目录结构：

model-00001-of-00007.safetensors
model-00002-of-00007.safetensors
...
model-00007-of-00007.safetensors
model.safetensors.index.json
config.json
tokenizer.json
generation_config.json
...

含义如下：

文件名 含义
model-00001-of-00007.safetensors 模型参数的第 1 个分片，共 7 个
model.safetensors.index.json 记录每个权重张量存储在哪个分片中（索引文件）
config.json 模型结构描述
tokenizer.json / merges.txt 分词器文件
generation_config.json 文本生成策略配置

🧠 safetensors 格式简析

safetensors 是一种由 Hugging Face 社区主导开发的安全、快速、零拷贝的模型权重保存格式，用于替代早期的 .bin（PyTorch pickle）格式。

✅ 相比 **.bin** 格式的优势：

特性 .bin .safetensors
安全性（避免执行 pickle） ❌ 可能执行恶意代码 ✅ 完全静态数据
加载速度（零拷贝 mmap） 较慢 ✅ 极快
分片支持 ✅ ✅
通用性（兼容 PyTorch） ✅ ✅（HuggingFace 专用）

🔍 文件内部结构

你不能直接打开 .safetensors 文件，但可以用 safetensors 官方库读取其中内容：

from safetensors import safe_open

with safe_open("model-00001-of-00007.safetensors", framework="pt") as f:
    for name in f.keys():
        tensor = f.get_tensor(name)
        print(name, tensor.shape)

这些 name 就是模型的权重名（如：transformer.h.0.attn.q_proj.weight），对应模型层。

📦 **model.safetensors.index.json** 作用

这个 JSON 文件告诉框架：

  • 所有参数都有哪些

  • 每个参数在哪个 .safetensors 分片中

  • 每个 tensor 的形状与数据类型

示例结构如下：

{
  "metadata": {
    "total_size": 54123342123
  },
  "weight_map": {
    "transformer.h.0.attn.q_proj.weight": "model-00001-of-00007.safetensors",
    "transformer.h.0.attn.k_proj.weight": "model-00001-of-00007.safetensors",
    ...
  }
}

这样框架就能在多个分片中找到每个参数的位置。

🛠️ 如何加载含 **.safetensors** 的模型？

使用 Hugging Face Transformers 会自动识别：

from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("your_model_dir", trust_remote_code=True)

框架会：

  • 加载 config.json 构建模型结构

  • 加载 safetensors.index.json 映射文件

  • 从多个 .safetensors 分片中加载权重

📤 如果你要保存为 **.safetensors**

from transformers import AutoModelForCausalLM

model.save_pretrained("your_dir", safe_serialization=True)

它会自动生成：

  • 分片的 model-xxxx-of-yyyy.safetensors

  • model.safetensors.index.json

你也可以设置 max_shard_size 控制分片大小（如 "2GB"）。

✅ 总结

项目 内容
文件名 model-00001-of-000XX.safetensors
作用 存储 Transformer 模型参数的分片（权重）
搭配使用 model.safetensors.index.json 提供索引
加载方式 自动由 Hugging Face Transformers 识别
替代格式 更快、更安全的 .bin 替代品
应用场景 大模型分布式权重管理，私有部署，安全模型分发

3.5 model.safetensors.index.json

model.safetensors.index.json 是 Hugging Face Transformers 在使用 .safetensors 格式保存大模型权重时生成的 索引文件，用于记录 每个模型参数（tensor）在哪个分片文件中，让模型加载器能正确分布式加载多个 .safetensors 文件。

🧠 一句话总结

model.safetensors.index.json 是多分片 .safetensors 权重文件的目录映射表，记录了每个权重张量的文件位置。

📦 为什么需要它？

当模型很大（例如 7B/14B/70B），所有参数无法放进一个 .safetensors 文件时，会被拆成多片，比如：

model-00001-of-00007.safetensors
model-00002-of-00007.safetensors
...
model-00007-of-00007.safetensors

这时就需要一个索引文件告诉你：

  • 每个 tensor 存在哪个分片文件里

  • 所有权重一共多大

📄 文件结构详解

{
    "metadata": {
        // 总大小（字节）
        "total_size": 21011769344
    },
    "weight_map": {
        // 嵌入层权重文件
        "model.embed_tokens.weight": "model-00001-of-00005.safetensors",
        // 第0层自注意力q_proj的权重文件
        "model.layers.0.self_attn.q_proj.qweight": "model-00001-of-00005.safetensors",
        "model.layers.0.self_attn.q_proj.qzeros": "model-00001-of-00005.safetensors",
        "model.layers.0.self_attn.q_proj.scales": "model-00001-of-00005.safetensors",
        "model.layers.0.self_attn.q_proj.bias": "model-00001-of-00005.safetensors",

一个典型的 model.safetensors.index.json 文件内容如下（已格式化）：

{
  "metadata": {
    "total_size": 13789162534  // 所有分片的总大小（字节数）
  },
  "weight_map": {
    "model.embed_tokens.weight": "model-00001-of-00007.safetensors",
    "model.layers.0.self_attn.q_proj.weight": "model-00001-of-00007.safetensors",
    "model.layers.0.self_attn.k_proj.weight": "model-00001-of-00007.safetensors",
    ...
    "lm_head.weight": "model-00007-of-00007.safetensors"
  }
}

🧩 字段解释

字段 类型 含义
metadata.total_size int 所有权重总大小（字节数）
weight_map dict key 为参数名，value 为对应的分片文件名

例如：

"model.layers.42.mlp.down_proj.weight": "model-00006-of-00007.safetensors"

表示这一层的参数在第 6 个权重分片中。

🛠️ 使用方式

当你用 Transformers 的 .from_pretrained() 加载 safetensors 权重时，它会：

  1. 读取 config.json 建好模型结构

  2. 检查是否有 model.safetensors.index.json

  3. 根据 weight_map 去每个分片 .safetensors 文件加载参数

你无需手动操作。

from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("path/to/model", trust_remote_code=True)

✏️ 自定义用法（高级）

你可以修改或生成自己的 model.safetensors.index.json，例如：

  • 加载部分权重：比如只加载 encoder 层用于微调

  • 重新分片：将一个大文件拆成多个分片

工具包支持：

from safetensors.torch import load_file
from transformers import PreTrainedModel

# 可读取特定 safetensors 文件
tensors = load_file("model-00001-of-00007.safetensors")

📌 补充说明

  • .index.json 是 只读辅助文件，不包含参数值本身

  • 不可缺失：如果有多个分片，必须存在此文件，否则加载会报错

  • 对应 .bin 的同类文件叫 pytorch_model.bin.index.json

✅ 总结

项目 内容
文件名 model.safetensors.index.json
作用 记录每个模型参数在哪个 .safetensors 分片中
用于 自动多分片加载、分布式部署、节省内存
典型配套文件 model-00001-of-00007.safetensors 等多个分片

# Qwen1.5-32B-Chat-AWQ


## Introduction

Qwen1.5 is the beta version of Qwen2, a transformer-based decoder-only language model pretrained on a large amount of data. In comparison with the previous released Qwen, the improvements include: 

* 8 model sizes, including 0.5B, 1.8B, 4B, 7B, 14B, 32B and 72B dense models, and an MoE model of 14B with 2.7B activated;
* Significant performance improvement in human preference for chat models;
* Multilingual support of both base and chat models;
* Stable support of 32K context length for models of all sizes
* No need of `trust_remote_code`.

For more details, please refer to our [blog post](https://qwenlm.github.io/blog/qwen1.5/) and [GitHub repo](https://github.com/QwenLM/Qwen1.5).
<br>

## Model Details
Qwen1.5 is a language model series including decoder language models of different model sizes. For each size, we release the base language model and the aligned chat model. It is based on the Transformer architecture with SwiGLU activation, attention QKV bias, group query attention, mixture of sliding window attention and full attention, etc. Additionally, we have an improved tokenizer adaptive to multiple natural languages and codes. For the beta version, temporarily we did not include GQA (except for 32B) and the mixture of SWA and full attention.

## Training details
We pretrained the models with a large amount of data, and we post-trained the models with both supervised finetuning and direct preference optimization.

## Requirements
The code of Qwen1.5 has been in the latest Hugging face transformers and we advise you to install `transformers>=4.37.0`, or you might encounter the following error:

KeyError: ‘qwen2’


## Quickstart

Here provides a code snippet with `apply_chat_template` to show you how to load the tokenizer and model and how to generate contents.

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

    "Qwen/Qwen1.5-32B-Chat-AWQ",
    torch_dtype="auto",
    device_map="auto"
)

prompt = "Give me a short introduction to large language model."

    {"role": "system", "content": "You are a helpful assistant."},

]

    messages,
    tokenize=False,
    add_generation_prompt=True
)

    model_inputs.input_ids,
    max_new_tokens=512
)
generated_ids = [
    output_ids[len(input_ids):] for input_ids, output_ids in zip(model_inputs.input_ids, generated_ids)
]

response = tokenizer.batch_decode(generated_ids, skip_special_tokens=True)[0]

3.8 tokenizer.json

tokenizer.json 是 Hugging Face Transformers 分词器目录中最核心的文件之一，它是Tokenizer 的完整序列化文件，包括词表、预处理规则、正则、特殊 token 映射、分词算法逻辑等。

🧠 一句话理解

tokenizer.json 是 tokenizer 的所有行为和词表信息的统一打包版本，用于快速加载和复现 tokenizer 行为，尤其在使用 fast tokenizer 时。

🔍 它和其它文件有何区别？

文件 作用 说明
tokenizer_config.json 参数设置 控制 tokenizer 运行行为（如是否加 bos_token）
tokenizer.json 主体 保存完整 fast tokenizer 定义，包括词表、merge、pretokenizer 等
vocab.json + merges.txt GPT/BPE 模型词表 用于 slow tokenizer 的构建
special_tokens_map.json 映射 <pad>、<eos> 这些符号的实际字符串/ID

tokenizer.json 是 Fast Tokenizer（Rust 实现）专用文件，可以替代 vocab.json 和 merges.txt，因此更快、更便携。

🔧 关键字段解释

字段名 说明
model 分词模型结构，如 BPE / WordPiece，含词表和合并规则
vocab 单词到 token ID 的映射
merges 合并规则（仅用于 BPE）
normalizer 正规化规则，如 Unicode 规范化、lowercasing 等
pre_tokenizer 分词前的处理，如空格拆分、正则
post_processor 分词后的处理，如添加 <bos>、</s> 等特殊 token
decoder 将 token ID 序列还原为字符串
added_tokens 用户添加的特殊 token，比如 <user>, <bot> 等
padding / truncation padding 和截断规则，决定输入对齐策略

tokenizer.save("tokenizer.json")

📝 和 fast tokenizer 的关系

特性 slow tokenizer fast tokenizer (tokenizer.json)
加载速度 慢 快（Rust 实现）
是否需要 vocab/merges 是 不需要（已合并到 tokenizer.json）
多语言支持 有 更强
正则/pipeline 细节可配置性 较弱 很强（支持 pretokenizer/normalizer/postprocessor）

总结 ✅

属性 内容
文件类型 JSON
用途 描述 tokenizer 全部行为，用于 fast tokenizer 加载
是否必须 不是必须，但存在时优先使用
和 vocab/merges 的关系 可以替代，功能更完整
修改方式 可通过 tokenizers 库创建或修改
建议 模型训练或部署推荐使用 tokenizer.json，尤其在需要高性能时

3.9 vocab.json

vocab.json 是 Hugging Face Tokenizer 模型中用于存储**词汇表（vocabulary）**的文件，常见于基于 BPE（Byte Pair Encoding）或 WordPiece 等子词分词算法的模型，例如 GPT、BERT、Roberta、LLaMA 等。

✅ 一句话理解

vocab.json 定义了「token 到 ID 的映射关系」，是分词器的核心文件之一。

📦 文件结构示例

{
  "the": 0,
  "Ġthe": 1,
  "a": 2,
  "Ġa": 3,
  "apple": 1000,
  "##ple": 1001,
  "<pad>": 50256,
  "<eos>": 50257
}

  • key：token（字符串），可以是单词、子词、符号或特殊 token

  • value：整型 ID，用于将 token 转为模型可用的输入

Ġ 表示前面有空格（在 Roberta/BPE 中常见） ## 表示这个词是接在前一个词后面的（WordPiece 标记）

🔍 它与其它文件的区别

文件 作用 是否必须 快速说明
vocab.json token ➜ ID 映射 是（slow tokenizer） 分词后映射成整数 token ID
merges.txt BPE 合并规则 是（BPE 模型） 指定如何从字符对合并出 token
tokenizer.json Fast tokenizer 全部行为 否 打包了 vocab 和 merges，也更快
tokenizer_config.json 加载 tokenizer 的配置项 否 控制是否添加特殊 token 等行为
special_tokens_map.json 特殊 token 的 ID/映射 否 控制 ,  等的定义

🔧 应用方式

加载模型 tokenizer 时会自动用到：

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("gpt2")  # 会读取 vocab.json + merges.txt
tokens = tokenizer.tokenize("The apple is red.")
ids = tokenizer.convert_tokens_to_ids(tokens)

你也可以手动加载：

import json

with open("vocab.json") as f:
    vocab = json.load(f)
print(vocab["apple"])  # 输出对应的 token ID

🏗 如何生成 vocab.json？

通常是通过训练分词器：

from tokenizers import Tokenizer, models, trainers, pre_tokenizers

tokenizer = Tokenizer(models.BPE())
tokenizer.pre_tokenizer = pre_tokenizers.Whitespace()

trainer = trainers.BpeTrainer(vocab_size=10000, special_tokens=["<pad>", "<eos>"])
tokenizer.train(["corpus.txt"], trainer)

tokenizer.model.save(".", "my-tokenizer")  # 输出 vocab.json + merges.txt

🚀 在推理中的作用

在推理时，文本输入流程如下：

文本输入 → 分词器 → token 序列 → vocab.json 查 ID → 模型输入

反向输出流程：

模型输出 token ID → vocab.json 反查 token → 拼接成文本

所以它是编码与解码的基础。

✅ 总结

属性 说明
文件类型 JSON（键为字符串 token，值为整数 ID）
用途 供 slow tokenizer 使用；token ↔ ID 映射
依赖 通常与 merges.txt 配合使用
被谁用 AutoTokenizer, PreTrainedTokenizer 等
是否可替代 若有 tokenizer.json，则可不再使用它

4、总结

Hugging Face 模型目录结构是用于保存一个预训练模型（及其 tokenizer、配置等）的完整打包形式，目的是为了方便模型的加载、共享、部署和推理。下面为你总结模型目录的标准构成、每个文件的作用、是否必须、以及它们之间的关系。

✅ 1. 目录结构总览

一个典型的 Hugging Face 模型目录如下：

/your-model-dir/
├── config.json
├── generation_config.json
├── pytorch_model.bin / model.safetensors
├── model.safetensors.index.json (如为分片模型)
├── tokenizer_config.json
├── tokenizer.json
├── vocab.json
├── merges.txt (如为 BPE)
├── special_tokens_map.json
├── README.md

📁 2. 各文件功能详解

文件名 必须 类型 作用
config.json ✅ 是 模型配置 定义模型架构参数（层数、隐藏维度、dropout 等）
pytorch_model.bin / model.safetensors ✅ 是 模型权重 保存模型的预训练参数（PyTorch 格式 / safetensors 更安全）
model.safetensors.index.json 🚫 否 权重索引 用于分片模型（多块 .safetensors 的索引信息）
tokenizer_config.json ✅ 是 tokenizer 配置 控制 tokenizer 行为，比如是否小写、是否添加 BOS/EOS 等
tokenizer.json 🚫 否 Fast tokenizer Hugging Face 的 Rust 实现 tokenizer，速度快，包含 vocab+merges
vocab.json ✅ 是 词表（token → id） 分词器词典，主要用于 slow tokenizer
merges.txt ⚠️ 视分词器类型 BPE 合并规则 仅用于 BPE（GPT、Roberta 等）
special_tokens_map.json 🚫 否 特殊 token 映射 映射 、、 等到对应 ID
generation_config.json 🚫 否 推理配置 定义采样策略（如 temperature, top_k, repetition_penalty 等）
README.md 🚫 否 文档 模型说明文档（在 Hugging Face hub 上展示）

🧠 3. 必须 vs 可选文件汇总

✅ 必须文件（用于模型加载）

  • config.json

  • pytorch_model.bin 或 model.safetensors

  • tokenizer_config.json

  • vocab.json

⚠️ 根据模型类型必须

  • merges.txt：如果使用 BPE tokenizer（如 GPT、Roberta）

🚫 可选但推荐

  • tokenizer.json：推荐用于 fast tokenizer，加快速度

  • generation_config.json：如模型用于生成任务（文本生成、聊天）

  • special_tokens_map.json：对话模型、翻译、QA 常用

  • README.md：用于模型说明和文档展示

  • model.safetensors.index.json：当模型是分片结构（sharded）时才出现

📦 4. 加载时工作机制

Hugging Face 的 AutoModel 和 AutoTokenizer 会根据目录内容自动判断使用哪种文件：

from transformers import AutoModelForCausalLM, AutoTokenizer

model = AutoModelForCausalLM.from_pretrained("./your-model-dir")
tokenizer = AutoTokenizer.from_pretrained("./your-model-dir")

它会依次尝试加载：

  • 权重：model.safetensors > pytorch_model.bin

  • tokenizer：tokenizer.json > vocab.json + merges.txt

  • 特殊 token：special_tokens_map.json

  • 推理策略：generation_config.json

🔍 5. 示例应用流程

文本 → tokenizer.json/vocab.json → token ID → 模型(config+权重) → 输出 token ID → 反向 tokenizer → 文本输出

✅ 总结一句话

Hugging Face 模型目录包含了“模型结构（config）+权重+分词器+推理策略”的完整组件，是部署、共享、加载模型的标准打包格式。
